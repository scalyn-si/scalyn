Who does what

Your five core agents stay at the centre. I added an Orchestrator to plan and route work, a Quality Reviewer as the human-review gate your plan insists on, and an Analytics agent so every engagement ends with numbers you can track. The Content Creator leads four sub-agents.

How it fits together

Architecture

Agents never talk to each other directly. Each one reads the client brief plus the outputs it depends on from a shared growth file, writes its own section back, and the Orchestrator decides what runs next.

Flow

Content and Sales run in parallel once the marketing strategy exists. Quality Reviewer reads everything before the client sees it.

Shared state: the growth file

One JSON document per client engagement. Every agent reads from it and writes only its own key. In the no-code build this is a Google Sheet row plus a Doc; in the code build it is a table in SQLite or Postgres.

{
  "client_id": "brightpath-2026-10",

Design rules

Orchestration

  • Each agent declares its dependencies; a runner starts any agent whose inputs are ready (max 3 at once).
  • Agents return strict JSON in a fixed shape, so outputs can be checked, rendered and exported.
  • If an agent fails, its dependents are blocked, not guessed. Re-run just that agent.

Human review gates

  • Gate 1, after the Orchestrator: confirm goal and answer its client questions.
  • Gate 2, after Marketing: approve positioning before content is written.
  • Gate 3, after Quality Reviewer: fix every must-fix item before delivery.

Honesty guardrails

  • No invented statistics, company names, people or phone numbers.
  • Market facts are labelled as hypotheses until interviews confirm them.
  • No guaranteed sales; targets are stated as targets.

Cost control

  • Cache identical runs; re-run single agents instead of the whole pipeline.
  • Use a smaller, cheaper model for sub-agents and the localizer once quality is proven.
  • Trim upstream context: each agent only gets the sections it depends on.

Data & privacy

  • Collect only business information, not customer personal data, at intake.
  • Lead trackers hold public business info; never scrape private numbers.
  • API keys stay in environment variables, never in a public repo.

Build stack, in two stages

Stage A · no-code · weeks 1–4

Form → Sheet → n8n → LLM → Doc

  • Google Form collects the brief into a Sheet.
  • An n8n workflow triggers on the new row and calls each agent prompt in order through an LLM node.
  • Each JSON output is written to its own Sheet column; a final node fills a Google Doc template.
  • You review the Doc, fix QA items, then send it.
Stage B · code · months 3–6

Python service with a DAG runner

  • FastAPI backend: POST /runs, GET /runs/{id}, POST /runs/{id}/agents/{agent}/rerun.
  • Agent registry: name, prompt template, output schema, dependencies (the same table as the Agents tab).
  • Validate every output against its schema (e.g. with Pydantic) and retry once on failure.
  • Simple web front end like this prototype; Postgres for growth files; optional framework such as LangGraph or CrewAI only if the plain runner gets painful.

Do you need more agents?

Three additions are worth it now and are already in the prototype. Four more are worth adding only after clients ask for that work twice.

Added now

Orchestrator

Without it, each agent works from the raw brief and they contradict each other. It sets one objective and briefs everyone.

Added now

Quality Reviewer

Your plan's core promise is human-reviewed output. This agent prepares that review: it flags invented facts, guarantees, inconsistencies and privacy risks.

Added now

Turns the plan into KPIs, a tracking sheet and a weekly action plan, which is what justifies a monthly retainer.
